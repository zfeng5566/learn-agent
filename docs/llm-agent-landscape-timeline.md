## 1. 先理清概念：LLM 落地的 6 种形态

讨论框架之前，先把「落地形态」分清楚，否则选型必然跑偏。工程上真正存在的形态只有这 6 种：

| 形态 | 一句话定义 | 典型业务 | 技术关键词 |
|---|---|---|---|
| **F1 能力点嵌入** | 把模型当一个函数，塞进已有系统的某一步 | 评论分类、工单打标、搜索相关性、风控文本识别 | 分类/抽取、结构化输出、批处理 |
| **F2 内容生成** | 人给指令，模型产出可编辑的草稿 | 营销文案、商品描述、报告初稿、翻译 | Prompt 工程、模板、人工终审 |
| **F3 知识问答（RAG）** | 先检索企业私有数据，再让模型基于它回答 | 企业知识库、客服助手、合同/制度问答 | 向量库、切块、重排、引用溯源 |
| **F4 Copilot 嵌入式助手** | 在用户干活的界面里提供上下文建议 | 代码补全、BI 取数、CRM 写跟进记录 | 上下文注入、低延迟、diff 预览 |
| **F5 Agent 自动执行** | 模型自己决定调哪些工具、循环多步直到完成 | 自动化排障、数据分析、测试修复、流程 RPA 替代 | 工具调用、状态机、权限与审批、重试 |
| **F6 多 Agent 协作** | 多个带角色/专长的 Agent 分工再汇总 | 深度研究报告、大规模代码重构、跨系统协同 | 编排、消息传递、子任务分发、评估 |

**一句话经验**：绝大多数企业真正跑到生产并产生收益的，是 **F1 / F3 / F4**；F5 需要配套权限与回滚才敢上；F6 在 2025 年之前基本是 Demo，2025 年起才在「编码」和「研究」两个垂类站住。

## 2. 2018–2020：模型能力点时代

### 落地形态
只有 **F1 能力点嵌入**。彼时模型不会「聊天」，是当作一个 NLP 任务模型来用的：输入一段文本，输出一个标签或一段抽取结果。做法是「下载预训练模型 → 用自己标注的几千条数据微调 → 导出成服务」。

### 开源框架

| 时间 | 框架 | 用途 | 业务形态 |
|---|---|---|---|
| 2018-10 | **Hugging Face Transformers** | 预训练模型的统一加载/微调/推理接口，把 BERT、GPT-2 等模型的调用方式标准化 | 一切 F1：文本分类、NER、相似度召回；至今仍是模型生态的事实标准 |
| 2019~2020 | **Sentence-Transformers** | 产出句向量（Embedding） | 语义搜索、相似问匹配、推荐召回 —— 这是后来 RAG 的前身 |
| 2019~2020 | **FAISS**（Facebook） | 向量相似度检索库 | 大规模向量召回，后来成为各向量数据库的底层 |
| 2020-06 | **GPT-3 API**（闭源，但是分水岭） | 第一次让「不微调、只写提示词」就能用 | 催生了 F2 |

### 这个阶段的业务真相
- 成本在**数据标注**，不在模型。
- 产出是一个「准确率 92%」的接口，交付形式是微服务，和传统机器学习项目没有区别。
- 没有「Agent」概念。

## 3. 2021–2022.11：Prompt 即产品

### 落地形态
**F2 内容生成**成立，**F4 Copilot** 第一次出现。

关键变化：GPT-3 之后，能力交付方式从「微调一个模型」变成「写一段 Prompt」。这让产品迭代周期从「周」缩短到「小时」，于是出现了一批「套壳即产品」的公司（文案生成类 SaaS）。

| 时间 | 事件/框架 | 用途 | 业务形态 |
|---|---|---|---|
| 2021-06 | **GitHub Copilot**（技术预览） | 代码补全 | F4 的第一个规模化成功案例，证明「嵌在用户工作流里」比「另开一个聊天窗口」价值高得多 |
| 2022-08 | **Stable Diffusion** 开源 | 文生图 | 带动了「开源权重 + 本地部署 + 社区生态」这条路径的信心，是 2023 年 LLM 开源爆发的预演 |
| **2022-10** | **LangChain** 首次开源 | 把「Prompt 模板 + 模型调用 + 工具 + 记忆 + 链式组合」抽象成统一接口 | 此时主要用于 F2/F3 的快速搭建，是后面两年所有讨论的中心 |
| **2022-11** | **GPT Index**（后改名 **LlamaIndex**） | 专注「把私有数据灌给 LLM」：加载器、切块、索引、查询 | F3 知识问答的专用框架，企业知识库的起点 |
| 2022-11-30 | **ChatGPT 发布** | —— | 分水岭：对话成为默认交互形态，企业开始立项 |

### 为什么 LangChain 和 LlamaIndex 在 ChatGPT 之前就出现了
因为 GPT-3 API 已经暴露了两个工程痛点：①Prompt 拼装散落在业务代码里无法复用 ②模型不知道公司内部数据。这两个框架分别解决了这两件事 —— 这也是它们各自的定位，一直没变：**LangChain 管「编排」，LlamaIndex 管「数据接入」**。

## 4. 2022.11–2023：RAG 元年与 Agent 第一次狂热

这一年信息密度最高，拆成四条线。

### 4.1 时间线

| 时间 | 事件/框架 | 用途 | 业务形态 |
|---|---|---|---|
| 2023-02-24 | **LLaMA** 权重泄露/开放研究 | —— | 开源模型生态起点 |
| 2023-03-10 | **llama.cpp** | 用 C/C++ 做 CPU/量化推理，让大模型跑在笔记本上 | 私有化部署、数据不出域的强合规场景（金融、政务、医疗） |
| 2023-03-13 | **Alpaca / 后续 Vicuna** | 指令微调方法与数据集范式 | 证明「小模型 + 好数据」可低成本得到可用对话模型 |
| 2023-03 | **PEFT / LoRA**（Hugging Face） | 参数高效微调，只训少量增量参数 | 行业术语适配、特定格式输出、风格对齐；成本从几十万降到几千 |
| 2023-03-14 | GPT-4 | —— | 能力跨过「可用于生产推理」的门槛 |
| 2023-03 | **Semantic Kernel**（微软） | C#/Java/Python 的 LLM 编排 SDK，强调 Plugin 与规划器 | 面向 .NET / Java 企业技术栈的集成，**Java 团队的主要选择之一** |
| 2023-03-30 | **AutoGPT** | 让 LLM 自主循环「思考→调工具→反思」直到完成目标 | F5 的概念验证。实际极不可控（死循环、烧 token、无法中断），但它定义了后来所有 Agent 框架要解决的问题 |
| 2023-04 | **BabyAGI** | 任务列表驱动的自主 Agent（更小更易读） | 教学价值极高，是理解 Agent 循环的最佳入门代码 |
| 2023-04~05 | **Dify** 开源 | 可视化 LLM 应用平台：编排、RAG、数据集、发布为 API | **企业落地主力**：业务人员拖拽建应用，研发只提供数据与工具；F2/F3 的交付效率提升一个数量级 |
| 2023-05~06 | **Chroma / Qdrant / Milvus / Weaviate / pgvector** 集中走红 | 向量数据库 | F3 的存储底座。其中 **pgvector** 对已有 PostgreSQL 的团队是「零新增组件」方案 |
| **2023-06-13** | **OpenAI Function Calling** | 模型输出结构化的函数调用意图 | **真正的分水岭**：Agent 从「解析自然语言猜意图」变成「稳定拿到 JSON」。F5 从此具备工程可行性 |
| 2023-06-20 | **vLLM** | 高吞吐推理引擎（PagedAttention、连续批处理） | 自托管模型的性能底座，吞吐相比朴素实现提升数倍，是私有化部署成本可控的关键 |
| 2023-07 | **Ollama** | 一条命令在本机跑模型，自动管理权重与量化 | 开发期本地调试、离线环境、边缘部署；大幅降低入门门槛 |
| 2023-07-18 | **Llama 2**（可商用） | —— | 企业私有化部署从「法律风险」变成「可签合同」 |
| 2023-07~ | **Text Generation Inference (TGI)** | Hugging Face 的生产级推理服务 | 与 vLLM 同类，偏 HF 生态 |
| 2023-09 | **AutoGen**（微软） | **多 Agent 对话式协作**：Agent 之间互相发消息、可嵌入人类节点、可执行代码 | F6 的第一个严肃框架。业务形态：数据分析（写代码→跑→看报错→改）、研究型任务 |
| 2023-09-27 | **Mistral 7B** | —— | 小模型质量跃升，端侧/低成本路线成立 |
| 2023-10 | **DSPy**（原 DSP） | 把 Prompt 当成「可优化参数」，用数据和指标自动编译提示词与少样本示例 | 对准确率敏感的 F1/F3 任务：用评估集自动调优，摆脱人工瞎改 Prompt |
| 2023-11 | **LangChain + LangSmith**（可观测） | 调用链追踪、Prompt 版本、评估 | 从「Demo 跑通」走向「生产可排障」的必要设施 |
| 2023 全年 | **Flowise / LangFlow / FastGPT** | 低代码可视化编排 | 与 Dify 同生态位，面向「业务自助搭建」 |
| 2023 全年 | **Haystack**（deepset） | 偏检索与问答管线的工程化框架 | 搜索团队出身的 F3 方案，管线概念清晰 |

### 4.2 这一年的落地真相

- **RAG 吃掉了 80% 的企业预算**。原因简单：企业要的是「基于我的制度/手册/工单回答」，而不是通用聊天。典型项目：企业知识库、智能客服一线分流、售前产品问答。
- **Agent 大面积失败**。AutoGPT 类项目在真实业务里不可用，原因不是模型不行，是**没有状态管理、没有中断点、没有权限边界、没有失败回滚**。2024 年的框架全部在补这四项。
- **私有化部署成为中国市场的硬需求**，llama.cpp + vLLM + Ollama 这条线的权重远高于海外。

主题从「能不能做」转向「敢不敢上线」。

### 5.1 时间线

| 时间 | 框架 | 用途 | 业务形态 |
|---|---|---|---|
| **2024-01** | **LangGraph** | 用**有向图/状态机**描述 Agent：显式节点、边、条件分支、循环上限、**断点与人工介入**、状态持久化 | 这是 F5 真正能上生产的框架。业务形态：审批流中插入 Agent、带人工确认的工单处理、可重放排障 |
| ~2024-01 | **CrewAI** | 以「角色 + 任务 + 流程」描述多 Agent 团队，上手极快 | F6 的轻量选择：内容生产流水线（调研→写作→审校）、营销素材批产 |
| 2024 全年 | **LlamaIndex Workflows** | 事件驱动的编排（LlamaIndex 自己的 Agent 层） | 在已用 LlamaIndex 做 RAG 的项目里顺势加 Agent |
| 2024 全年 | **Instructor / Outlines / Pydantic AI(~2024-12)** | **强制结构化输出**：用 Pydantic 模型约束返回值，带校验与重试 | F1 的质量生命线。业务形态：发票/合同字段抽取、工单自动打标、把非结构化数据灌进数据库 |
| 2024 全年 | **LiteLLM** | 统一 100+ 模型供应商的调用接口，带路由、重试、限流、成本统计 | 多模型兜底与成本优化；国内常用于「主用某模型 + 失败切备用」 |
| 2024 全年 | **Langfuse / TruLens / RAGAS / DeepEval** | 可观测与评估：链路追踪、成本统计、RAG 质量打分（忠实度/相关性）、回归测试 | **决定项目生死的一层**。没有评估集的 LLM 项目，改 Prompt 等于赌博 |
| 2024-03 | **OpenDevin → OpenHands** | 开源的自主软件工程 Agent（读代码、改文件、跑测试） | F5 在「编码」垂类的开源代表 |
| 2024 全年 | **aider** | 终端里的 Git 感知编码 Agent，每步自动提交 | 单人开发者的真实生产力工具，**比大多数 Agent 框架更早被真正日常使用** |
| 2024-07 | **GraphRAG**（微软） | 用 LLM 抽实体关系建知识图谱，再做图上检索 | 解决朴素 RAG 答不了「全局性/汇总性」问题；代价是建图成本高。业务形态：尽调、情报分析、复杂文档集 |
| 2024 全年 | **重排与混合检索成为标配**（BGE-reranker、Cohere Rerank、BM25 + 向量混合） | 提升 F3 命中率 | 知识库从「能用」到「可信」的主要手段 |
| 2024-04 / 07 | Llama 3 / 3.1 405B | —— | 开源权重追上第一梯队的拐点 |
| 2024-10 | **Computer Use**（Anthropic） | 模型直接看屏幕、点鼠标、敲键盘 | 打开了「无 API 的老系统也能自动化」的路；2024 年可靠性仍低 |
| 2024 全年 | **browser-use / Playwright 驱动的浏览器 Agent** | 让 Agent 操作网页 | RPA 替代、信息采集、跨系统录入 |
| **2024-11-25** | **MCP（Model Context Protocol）** by Anthropic 开源 | **把「模型如何接工具/数据源」协议化**：一次实现一个 MCP Server，所有支持 MCP 的客户端都能用 | 彻底改变集成方式，见下节 |

### 5.2 2024 年的两个结构性变化

**变化一：Agent = 状态机，不是提示词。**
LangGraph 的流行说明了共识的形成：Agent 的可靠性来自**显式控制流**（哪一步、能循环几次、哪里停下来等人），不是来自更聪明的 Prompt。
> 对照后端经验：这就是把「一段 if-else 乱炖」重构成「状态机 + 事务 + 重试策略」。

**变化二：评估先行。**
2024 年起，成熟团队的开工顺序变成：**先建 50~200 条评估集 → 再写 Prompt / 建管线 → 每次改动跑回归**。没有这一步的项目，上线后无法迭代。

## 6. 2024.11–2025：协议标准化与编码 Agent 进生产

### 6.1 MCP：这两年最重要的工程变化

**问题**：2023–2024 年，每个 Agent 框架都有自己的「工具」定义方式。给 LangChain 写的工具，AutoGen 用不了；接一个内部系统，每换一个框架就重写一遍。N 个客户端 × M 个系统 = N×M 的集成工作量。

**MCP 的解法**：定义一套客户端/服务端协议。你把内部系统（数据库、工单系统、监控、文件库）封装成 **MCP Server**，任何支持 MCP 的客户端（IDE 插件、终端 Agent、聊天客户端）都能直接用。N×M 变成 N+M。

| 时间 | 事件 | 说明 |
|---|---|---|
| 2024-11-25 | Anthropic 开源 MCP 规范 + SDK（Python/TypeScript 等） | 协议 + 参考实现 + 一批官方 Server（文件系统、Git、数据库…） |
| ~2025-03 | OpenAI 宣布支持 MCP | 从「一家的协议」变成**事实标准** |
| ~2025-06 | MCP 规范更新（鉴权/OAuth、流式传输等完善） | 具备企业接入条件 |

**对企业的业务形态影响**：集成工作从「给 Agent 写插件」变成「给公司建 MCP Server 目录」。这是一个**平台化**的动作 —— 一次封装，所有 Agent 入口复用，和内部 OpenAPI 网关的定位非常像。

### 6.2 2025 时间线

| 时间 | 框架/事件 | 用途 | 业务形态 |
|---|---|---|---|
| ~2025-01 | **DeepSeek V3 / R1** 开源 | 高性价比 + 推理能力开源 | 直接压低了国内 LLM 应用的单位成本，很多「算不过来账」的场景（大批量 F1 处理）变得可行 |
| ~2025-03 | **OpenAI Agents SDK**（Swarm 的生产版） | 轻量 Agent + Handoff（移交）+ Guardrails + 内置追踪 | 极简派：不画图，用「Agent 之间移交」表达流程。适合客服分流类场景 |
| ~2025-04 | **A2A（Agent2Agent）** by Google 开源 | **Agent 之间**互相发现与协作的协议（MCP 管 Agent↔工具，A2A 管 Agent↔Agent） | 跨团队/跨厂商 Agent 协同；2025 年仍偏早期，实际采用远不及 MCP |
| ~2025 上半年 | **Claude Code / Codex CLI / Gemini CLI 等终端 Agent** | 在终端里读写代码库、跑命令、改测试 | **2025 年唯一大规模产生实际收益的 F5 场景**。业务形态：改 bug、写测试、批量重构、迁移升级 |
| 2025 全年 | **Model Context Protocol 生态**（各类 MCP Server） | 把内部系统暴露给 Agent | 企业 Agent 平台的标准接入层 |
| 2025 全年 | **verl / OpenRLHF / TRL** | 强化学习训练（含训 Agent 行为） | 头部团队自训专用 Agent；一般企业不碰 |
| 2025 全年 | **SWE-bench Verified / Terminal-Bench 等评测** | 衡量 Agent 真实能力 | 选型依据从「Demo 好看」变成「有基准分数」 |
| 2025 全年 | **Agentic RAG** | 让 Agent 自己决定检索几次、检索什么、是否要换查询 | F3 升级：复杂问题多跳检索，取代一次性召回 |
| ~2025 下半年 | **Agent Skills / Claude Agent SDK 等「可装载能力包」形态**（待核实细节） | 用文件夹 + 说明书的方式给 Agent 加领域能力，按需加载 | 把「公司内部规范/流程」做成可复用能力包，比写死在 Prompt 里更好维护 |
| ~2025-10 | **LangGraph 1.0 / LangChain 1.0**（待核实版本时间） | API 稳定化 | 对企业意味着可以长期依赖、不怕 breaking change |

### 6.3 2025 年落地形态总结

| 形态 | 2025 年实际状态 |
|---|---|
| F1 能力点 | ✅ 完全成熟，成本已低到可全量跑 |
| F2 内容生成 | ✅ 成熟，但同质化严重，不构成壁垒 |
| F3 RAG | ✅ 成熟，重点从「能检索」转向「检索质量 + 引用可核查」 |
| F4 Copilot | ✅ 编码领域规模化成功；CRM/BI/办公领域跟进中 |
| F5 单 Agent 自动执行 | 🟡 **编码**已进生产；其他领域要求「人工审批 + 可回滚」才敢上 |
| F6 多 Agent | 🟡 「深度研究」和「大规模代码任务」两个垂类站住，其余仍是 Demo |

## 7. 2025 下半年–2026：长时任务与 Agent 组织化（待核实）

> ⚠️ 以下为知识截止 2026-05 时的态势判断，**请以最新官方信息核对**。

观察到的方向：

1. **长时任务（long-horizon）成为主战场**
   从「一次对话完成一件事」转向「一个 Agent 跑几小时甚至几天」。工程重点随之变成：上下文压缩与交接、检查点与恢复、子 Agent 分发、预算与超时控制。框架层的体现是 sub-agent / 持久化状态 / 会话恢复变成一等公民。

2. **Agent 的「组织设计」问题**
   一旦有多个 Agent 长期运行，问题从「怎么调模型」变成「怎么分工、怎么汇报、谁有权限做什么」—— 这是组织与权限设计问题，不是模型问题。对应到工程：Agent 身份与鉴权、审计日志、操作白名单与审批网关。

3. **协议层收敛**
   MCP（Agent↔工具）已是标准；A2A（Agent↔Agent）仍在争夺期。企业的理性做法是：**工具层押 MCP，Agent 间协作先用自己的消息队列，不急于押协议**。

4. **评估与审计成为采购门槛**
   企业采购 Agent 方案时开始要求：可追溯的操作日志、可重放的执行链路、可量化的回归测试集。这一层的开源工具（Langfuse 等）地位上升。

5. **成本结构变化**
   开源模型（DeepSeek、Qwen 系列等）+ vLLM 自托管，让高频 F1/F3 场景的成本降到可以「全量跑」的程度；而 F5/F6 的 Agent 任务 token 消耗是 F3 的几十倍，**成本控制从「选便宜模型」变成「设计更少的循环」**。

## 9. 选型决策树

```
需求是什么？
│
├─ 把一段文本变成一个标签/几个字段（F1）
│   └─ 直接调模型 + Instructor/Pydantic 约束输出
│      不要上框架。真的不要。
│
├─ 基于公司内部文档回答问题（F3）
│   ├─ 文档 < 1 万篇、业务方要自己维护
│   │   └─ Dify / FastGPT（低代码平台，交付最快）
│   └─ 要深度定制检索策略
│       └─ LlamaIndex（数据接入）+ pgvector（已有 PG）或 Qdrant
│          必加：混合检索 + Reranker + 引用溯源
│
├─ 在用户干活的界面里给建议（F4）
│   └─ 没有框架能帮你。关键是上下文注入和延迟，自己写
│
├─ 要让它自己调工具、多步执行（F5）
│   ├─ 操作是只读的（查询、分析）
│   │   └─ LangGraph 或 OpenAI Agents SDK
│   └─ 操作会改数据/调外部系统
│       └─ LangGraph（要断点 + 人工确认 + 状态持久化 + 可重放）
│          必加：操作白名单、审批网关、审计日志、回滚方案
│
├─ 多角色协作（F6）
│   ├─ 内容流水线（调研→写→审）
│   │   └─ CrewAI（快）
│   └─ 需要互相质询 / 跑代码验证
│       └─ AutoGen
│
└─ 技术栈是 Java / .NET
    └─ Semantic Kernel；或 Python 侧做 Agent 服务 + Java 侧调 HTTP
       （后者更常见：Agent 层独立部署，业务系统只当调用方）
```

**跨所有分支的三件事（不做就别上线）**：
1. **评估集**：50~200 条真实问题 + 期望答案，每次改动跑一遍。
2. **可观测**：Langfuse 之类，能看到每次调用的输入输出、耗时、成本。
3. **MCP 化内部工具**：工具封装成 MCP Server，避免绑死某个框架。

## 10. 踩坑清单

按踩的人数排序：

1. **先选框架，后想需求**
   90% 的 LLM 项目实际只需要「调模型 + 约束输出 + 一个向量检索」。引入重框架带来的是调试困难和版本升级债。
   > 对照后端经验：这和「为了一个定时任务引入一整套工作流引擎」是同一个错误。

2. **RAG 效果差，第一反应是换模型**
   真实原因排序：①切块策略烂（表格/标题被切碎）②没有重排 ③没做查询改写 ④文档本身写得烂。换模型通常是收益最小的那一项。

3. **没有评估集就调 Prompt**
   改一版，感觉好了；再改一版，又感觉好了；三个月后不知道哪版最好。这不是迭代，是随机漫步。

4. **Agent 没有循环上限和预算上限**
   一个死循环能烧掉一个月的额度。LangGraph 之所以赢，核心就是它让这些上限变成显式配置。

5. **让 Agent 直接拿到生产库写权限**
   Agent 的错误不是「返回错值」，是「以完全自信的语气执行了错误操作」。所有写操作都应经过白名单 + 审批 + 可回滚。

6. **用 Agent 解决本该用代码解决的问题**
   「每天把 A 表数据同步到 B 表」不需要 Agent，需要一个定时任务。Agent 适合的是**分支多到写不完 if-else、且允许偶尔出错**的场景。

7. **多 Agent 是为了「看起来高级」**
   每增加一个 Agent，就增加一次信息传递损耗和一份 token 成本。单 Agent 能做的，不要拆成三个。

8. **把公司内部规范写死在超长 Prompt 里**
   难维护、难复用、挤占上下文。应该做成可按需加载的能力包 / MCP Server / 检索得到的文档。

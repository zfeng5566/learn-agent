## 第一课：LLM 是什么？——一个超级"接龙"高手

### 1.1 先从手机输入法说起

你一定用过手机输入法。当你打出"今天天气"，输入法会在上方提示："真好"、"怎么样"、"不错"。

输入法并不"懂"天气，它只是见过太多人在"今天天气"后面打"真好"，于是猜你大概也想打这个。

**LLM（Large Language Model，大语言模型）本质上就是一个超级强化版的输入法联想。** 它做的事情只有一件：

> **给它一段文字，它猜"下一个字（词）"最可能是什么。**

就这么简单。ChatGPT、Claude、文心一言、通义千问……不管名字多花哨，核心都是这一件事。

### 1.2 一个字一个字地"接龙"

你可能会问：它只会猜下一个字，怎么能写出一整篇文章？

答案是：**不停地接龙**。

```
输入：  床前明月
猜下一个字：光
新输入：床前明月光
猜下一个字：，
新输入：床前明月光，
猜下一个字：疑
……
```

每猜出一个字，就把它拼回到原文后面，再猜下一个。像玩成语接龙一样，一直接下去，直到它猜出"结束"这个特殊信号为止。

我们用 Python 把这个"接龙循环"写出来。先假装我们已经有一个会猜字的"大脑"（这里用一本写死的小字典代替）：

```python
# 第一课：接龙循环
# 假装这是一个"大脑"：看到最后一个字，就知道下一个字是什么
fake_brain = {
    "床": "前", "前": "明", "明": "月", "月": "光",
    "光": "，", "，": "疑", "疑": "是", "是": "地",
    "地": "上", "上": "霜", "霜": "<结束>",
}

def generate(text):
    """不停地猜下一个字，拼到末尾，直到猜出 <结束>"""
    while True:
        last_char = text[-1]              # 看看最后一个字
        next_char = fake_brain[last_char]  # 问大脑：下一个是什么？
        if next_char == "<结束>":
            break
        text += next_char                  # 拼上去，继续接龙
    return text

print(generate("床"))   # 床前明月光，疑是地上霜
```

运行后会输出完整的诗句。**这段小代码的循环结构，和真正的 ChatGPT 生成回答的循环结构是一模一样的。** 区别只在于那个"大脑"：我们的是一本写死的小字典，真正的 LLM 是一个从海量文字里学出来的、极其复杂的"猜字机器"。

整本教程，其实就是在讲：**这个"大脑"是怎么造出来的，它为什么能猜得这么准。**

### 1.3 "大"在哪里？

LLM 名字里的三个词：

- **Large（大）**：读过的书多（几乎是整个互联网的文字量），脑子里的"旋钮"多（几十亿到上万亿个，后面会讲旋钮是什么）。
- **Language（语言）**：它处理的对象是文字。
- **Model（模型）**：它是一个"模仿规律的机器"，不是一个存满答案的数据库。

记住第三点非常重要：**LLM 不是在"查资料"，而是在"凭感觉接话"**。这一点会解释后面很多现象，比如它为什么会一本正经地胡说八道。

## 第二课：最笨的接龙——数一数"下一个字"

### 2.1 大脑从哪里来？

第一课里，我们的"大脑"是手写的。可世界上的句子无穷无尽，不可能手写。怎么办？

最朴素的想法：**拿一大堆文章来，数一数每个字后面最常跟着什么字。**

就像一个刚来中国的外国朋友，他不懂语法，但他每天听大家说话，默默记小本本：

- "吃"后面经常跟"饭"
- "喝"后面经常跟"水"、"茶"
- "你"后面经常跟"好"

记得多了，他也能"接"出像模像样的话来。

### 2.2 用 Python 实现"记小本本"

```python
# 第二课：从文章里统计"下一个字"
from collections import Counter, defaultdict

corpus = """
我爱吃苹果。我爱吃香蕉。我爱喝牛奶。
你爱吃苹果。他爱喝茶。我们爱学习。
我爱学习。我爱编程。
"""

# notebook["爱"] 记录的是：在"爱"后面，各个字分别出现过几次
notebook = defaultdict(Counter)
for i in range(len(corpus) - 1):
    current_char, next_char = corpus[i], corpus[i + 1]
    notebook[current_char][next_char] += 1

print("「爱」后面出现过：", dict(notebook["爱"]))
print("「吃」后面出现过：", dict(notebook["吃"]))
```

输出类似：

```
「爱」后面出现过： {'吃': 3, '喝': 2, '学': 2, '编': 1}
「吃」后面出现过： {'苹': 2, '香': 1}
```

看，这个小本本已经"学到"了一些规律：在"爱"后面，"吃"出现得最多。这就是最原始的"语言模型"，学术上叫 **二元模型（Bigram）**——只看前一个字来猜后一个字。

### 2.3 让它自己写句子

```python
# 接着上面的代码：每次都挑"出现次数最多"的那个字
def generate_greedy(start, length=8):
    text = start
    for _ in range(length):
        candidates = notebook[text[-1]]
        if not candidates:
            break
        best = candidates.most_common(1)[0][0]  # 最常见的下一个字
        text += best
    return text

print(generate_greedy("我"))
```

它可能会输出"我爱吃苹果。我爱吃"——看起来像话！但你很快会发现问题：它总在原地打转，因为它**只看最后一个字**。

### 2.4 小结

- 语言模型的知识，来自**大量阅读后总结出的规律**，不是人写死的规则。
- 最笨的做法是"数次数"，它已经能接出一点像样的话。
- 但只看一个字，视野太窄了。

## 第三课：看得更远——上下文为什么重要

### 3.1 一个字说明不了问题

请你接下一个字：

> "苹"

你可能会说"果"。但如果前面是这样呢：

> "我刚买了一台新的苹"

你会说"果"，但你脑子里想的是**手机**，不是水果。再看：

> "他打开了苹果"

接下来是"手机"、"电脑"，还是"罐头"？——只看"苹果"两个字根本判断不了，你需要看**更前面的内容**。

这些"前面的内容"，就叫做 **上下文（Context）**。

### 3.2 生活中的例子

你走进一家餐馆，服务员只听到你说了一个字"辣"，他不知道你要"辣一点"还是"不要辣"。但如果他听到了完整的"我不太能吃辣"，就明白了。

**看到的上下文越多，猜得越准。** 这是理解 LLM 的第二个关键。

### 3.3 那就多看几个字？

最直接的改进：不只看前 1 个字，而是看前 2 个、前 3 个字。

```python
# 第三课：看前 N 个字来猜下一个字
from collections import Counter, defaultdict

corpus = "我喜欢苹果手机。我喜欢苹果手机。我喜欢吃苹果。妈妈买了苹果派。"

def build_notebook(text, n):
    """记录：前 n 个字 -> 下一个字出现的次数"""
    book = defaultdict(Counter)
    for i in range(len(text) - n):
        context = text[i:i + n]
        book[context][text[i + n]] += 1
    return book

book1 = build_notebook(corpus, 1)
book3 = build_notebook(corpus, 3)

print("只看1个字「果」：", dict(book1["果"]))
print("看3个字「吃苹果」：", dict(book3["吃苹果"]))
print("看3个字「欢苹果」：", dict(book3["欢苹果"]))
```

输出：

```
只看1个字「果」： {'手': 2, '。': 1, '派': 1}
看3个字「吃苹果」： {'。': 1}
看3个字「欢苹果」： {'手': 2}
```

只看"果"时，它很犹豫；多看几个字后，它就很确定了。

### 3.4 但这条路走不通

既然看得多就准，那看前 100 个字不就好了？问题来了：

1. **组合爆炸**：前 100 个字的组合多到宇宙都装不下，你永远也收集不到足够的例子。
2. **不会举一反三**：小本本里记了"我喜欢吃苹果"，但没见过"我喜欢吃梨"，它就完全不知道"梨"后面接什么——哪怕"梨"和"苹果"明明都是水果。

人类不是这样的。你知道"苹果"和"梨"很像，所以见过"苹果很甜"，你自然能理解"梨很甜"。

**怎么让机器也明白"苹果和梨很像"？** 这就需要接下来两课的知识：Token 和 Embedding。

## 第四课：Token——模型眼里的"字"

### 4.1 机器不认识字

计算机只认识数字。所以第一步，要把文字切成小块，再给每一块编个号。这些小块，就叫 **Token（词元）**。

就像去银行办业务：你不叫"张三"，你叫"A037 号"。叫号系统只关心号码。

### 4.2 怎么切？

切法有很多种：

- **按字切**：`我 / 爱 / 吃 / 苹 / 果`
- **按词切**：`我 / 爱 / 吃 / 苹果`
- **折中切**：常见的词整块保留，罕见的词拆成小片。

现在的 LLM 基本都用"折中切"。比如英文单词 `unbelievable`，可能被切成 `un / believ / able`。这样做的好处是：

- 常见词一个 Token 搞定，效率高；
- 遇到没见过的新词（比如网络新梗），也能拆成认识的小块来理解，不会"不认识"。

### 4.3 用 Python 玩一个"叫号系统"

```python
# 第四课：一个极简的分词 + 编号系统
vocab = ["<未知>", "我", "爱", "吃", "苹果", "香蕉", "喝", "牛奶", "。"]
token_to_id = {tok: i for i, tok in enumerate(vocab)}

def tokenize(text):
    """贪心切词：每次尽量匹配最长的已知词"""
    tokens, i = [], 0
    while i < len(text):
        for size in (2, 1):                 # 先试 2 个字的词，再试 1 个字
            piece = text[i:i + size]
            if piece in token_to_id:
                tokens.append(piece)
                i += size
                break
        else:                               # 都不认识
            tokens.append("<未知>")
            i += 1
    return tokens

sentence = "我爱吃苹果。我爱喝可乐。"
tokens = tokenize(sentence)
ids = [token_to_id[t] for t in tokens]
print(tokens)  # ['我', '爱', '吃', '苹果', '。', '我', '爱', '喝', '<未知>', '<未知>', '。']
print(ids)     # [1, 2, 3, 4, 8, 1, 2, 6, 0, 0, 8]
```

你会发现，"可乐"不在词表里，变成了 `<未知>`。真正的 LLM 词表有几万到十几万个 Token，并且通过"折中切"几乎不会出现"未知"。

### 4.4 Token 对你有什么影响？

作为使用者，你会在很多地方碰到 Token 这个词：

- **计费**：大模型 API 按 Token 数收费，而不是按字数。
- **长度限制**：模型说"最多支持 20 万 Token"，指的是它一次能看的文字量。
- **奇怪的弱点**：问 LLM "strawberry 里有几个 r"，早期模型经常答错。因为它看到的不是一个个字母，而是 `straw / berry` 这样的块——就像让你数"银行卡号 A037"里有几个笔画，你根本没看到笔画。

## 第五课：Embedding——给每个词发一张"身份卡"

### 5.1 光有编号还不够

上一课里，"苹果"是 4 号，"香蕉"是 5 号。但编号只是个名字，4 号和 5 号之间没有任何关系——就像你家门牌是 401，并不代表你和 402 的邻居性格相似。

我们需要一种方式，让机器知道"苹果和香蕉很像，苹果和汽车不像"。

### 5.2 身份卡的比喻

想象我们给每个词发一张**身份卡**，上面写着它的各种特征：

| 词 | 能吃吗 | 是水果吗 | 是甜的吗 | 有轮子吗 | 是动物吗 |
|----|------|------|------|------|------|
| 苹果 | 是 | 是 | 是 | 否 | 否 |
| 香蕉 | 是 | 是 | 是 | 否 | 否 |
| 汽车 | 否 | 否 | 否 | 是 | 否 |
| 小猫 | 否 | 否 | 否 | 否 | 是 |

有了这张卡，机器一比对就知道：苹果和香蕉的卡几乎一样，所以它们很像；苹果和汽车的卡完全不同。

**这张"身份卡"，就是 Embedding（嵌入向量）的直观理解。**

### 5.3 用 Python 比较身份卡

```python
# 第五课：用"特征标签"感受 Embedding
id_cards = {
    "苹果": {"能吃", "水果", "甜", "红色", "圆的"},
    "香蕉": {"能吃", "水果", "甜", "黄色"},
    "西瓜": {"能吃", "水果", "甜", "圆的", "夏天"},
    "汽车": {"有轮子", "能载人", "金属"},
    "自行车": {"有轮子", "能载人", "金属", "环保"},
    "小猫": {"动物", "可爱", "有毛"},
}

def similar_words(word):
    """找出和 word 共同标签最多的词，从像到不像排序"""
    my_tags = id_cards[word]
    others = [w for w in id_cards if w != word]
    return sorted(others, key=lambda w: len(my_tags & id_cards[w]), reverse=True)

print("和「苹果」最像的：", similar_words("苹果"))
print("和「汽车」最像的：", similar_words("汽车"))
```

输出：

```
和「苹果」最像的： ['西瓜', '香蕉', '汽车', '自行车', '小猫']
和「汽车」最像的： ['自行车', '苹果', '香蕉', '西瓜', '小猫']
```

### 5.4 真正的 Embedding 有什么不同？

我们的身份卡是**人手写**的标签，而真正的 Embedding：

1. **标签不是人写的，是机器自己学出来的。** 机器读了海量文章后发现："苹果"和"香蕉"总出现在相似的句子里（"我买了一斤 ×× "、"×× 很甜"），于是自动把它们的身份卡调得很像。这就是语言学里的一句名言："**看一个词的朋友，就知道这个词是什么意思。**"
2. **标签数量很多。** 不是 5 个，而是几千个。而且这些"标签"人类往往说不清含义——它可能是某种"正式程度"、"情绪色彩"、"和食物有多相关"的混合。
3. **它不是"是/否"，而是"程度"。** 像调音台上的推子，每个特征都可以推到某个位置。

### 5.5 身份卡的神奇之处

身份卡学好以后，会出现一些很神奇的现象。最有名的例子：

> "国王" 的身份卡，去掉"男性"的特征，加上"女性"的特征，结果最接近 "女王"。

类似的还有：

> "北京" 之于 "中国"，就像 "东京" 之于 "日本"。

机器从来没有被教过"首都"这个概念，但它从文字中**自己领悟**出了这种关系。

现在回头看第三课的难题——"见过苹果很甜，没见过梨很甜"——有了身份卡，模型知道"梨"和"苹果"的卡很像，自然能推测"梨"后面也可能接"很甜"。**举一反三的能力，就是从这里来的。**

## 第六课：神经网络——一台有无数旋钮的机器

### 6.1 我们需要一台"猜字机器"

到目前为止，我们有了：
- Token：把文字切块编号；
- Embedding：给每块发一张身份卡。

接下来需要一台机器：**输入前面所有字的身份卡，输出"下一个字是什么"的猜测。**

这台机器就是 **神经网络（Neural Network）**。

### 6.2 调音台的比喻

想象一个巨大的调音台，上面有成千上万个旋钮。声音（输入）从一头进去，经过所有旋钮的调整，从另一头出来（输出）。

- 旋钮拧到不同位置，出来的声音就不同。
- 只要旋钮拧对了，任何杂乱的输入都能被调成你想要的输出。

神经网络就是这样一台调音台，那些旋钮叫做 **参数（Parameters）**。我们常听说的"70 亿参数的模型"、"千亿参数的模型"，指的就是**旋钮的数量**。

### 6.3 旋钮是怎么调好的？——"热了冷了"游戏

没有人能手动去拧几十亿个旋钮。那它们是怎么被调好的？

你一定玩过这个游戏：一个人藏东西，另一个人找，藏的人只说"热了"（离得近了）或者"冷了"（离得远了）。

神经网络的训练就是这个游戏：

1. 给机器看一句话的前半句："床前明月"，让它猜下一个字；
2. 机器一开始乱猜，说"狗"；
3. 我们告诉它：正确答案是"光"，你"冷了"；
4. 机器把每个旋钮**往能让"光"的可能性变大的方向，轻轻拧一点点**；
5. 换下一句话，重复上亿次。

我们用 Python 模拟一个只有**一个旋钮**的"热冷游戏"：

```python
# 第六课：用"热了/冷了"的反馈，一点点调好一个旋钮
import random

secret = 72          # 正确的旋钮位置（机器不知道）
knob = random.randint(0, 100)  # 机器一开始随便拧到一个位置
step = 8

for round_no in range(1, 30):
    if knob == secret:
        print(f"第 {round_no} 轮：旋钮在 {knob}，完全正确！")
        break
    hint = "太大了" if knob > secret else "太小了"
    print(f"第 {round_no} 轮：旋钮在 {knob}，老师说：{hint}")
    knob = knob - step if knob > secret else knob + step
    step = max(1, step // 2) if abs(knob - secret) < step else step  # 越接近，拧得越小心
```

运行几次你会看到：不管旋钮一开始在哪，经过一轮轮"热了冷了"的提示，它总能慢慢逼近正确位置。

真实的训练过程，只不过是把"一个旋钮"换成了"几百亿个旋钮"，把"猜一个数字"换成了"猜下一个字"，然后用数学方法高效地同时调整所有旋钮（这个方法叫 **反向传播**，你只需要记住它的作用是"告诉每个旋钮该往哪边拧"）。

### 6.4 重要的认识

- 训练完成后，**所有知识都"溶解"在旋钮的位置里**。模型里没有一句一句存着的原文，就像你学会骑自行车后，脑子里并没有一份"骑车说明书"。
- 所以，你没法打开模型找到"它在哪儿记住了李白是唐朝人"——这份知识分散在无数旋钮中。

## 第七课：注意力机制——读句子时该盯着哪儿看

这一课是现代 LLM 最核心的发明，请多花点时间。

### 7.1 一个让机器头疼的句子

> "小明把蛋糕放进了冰箱，因为**它**太热了。"
>
> "小明把蛋糕放进了冰箱，因为**它**太满了。"

两句话里的"它"分别指什么？

- 第一句："太热了"——蛋糕太热了，所以放进冰箱。"它"指**蛋糕**。
- 第二句："太满了"——冰箱太满了？那就放不进去了……其实这句话本身就有点别扭，但你一定会下意识地把"它"和**冰箱**联系起来，因为"满"通常描述容器。

你在读到"它"的时候，眼睛会**自动回头看**前面的"蛋糕"和"冰箱"，再结合后面的"热"或"满"来决定。

这种"读到某个词时，回头关注句子里与它最相关的词"的能力，就是 **注意力（Attention）**。

### 7.2 课堂上的比喻

想象一个班级，每个词是一个学生。现在"它"同学要搞清楚自己是谁，于是它在班里问了一圈：

- "它"问"小明"：你和我有关吗？小明说：关系不大。
- "它"问"蛋糕"：你和我有关吗？蛋糕说：我能被"热"描述，关系很大！
- "它"问"冰箱"：你和我有关吗？冰箱说：我是个电器，可能有点关系。
- "它"问"放进"：动词，关系不大。

问完一圈，"它"决定：**我 70% 是蛋糕，20% 是冰箱，10% 是其他**。然后它把这些同学的信息按比例"吸收"进自己的身份卡里。

经过这一步，"它"的身份卡就不再是一个空洞的代词了，而是带上了"蛋糕"的含义。

### 7.3 用 Python 模拟"问一圈"

真实的注意力分数是模型自己算出来的，这里我们手动给出"关联程度"，只为感受过程：

```python
# 第七课：模拟注意力——"它"在句子里找自己最该关注的词
sentence = ["小明", "把", "蛋糕", "放进", "冰箱", "因为", "它", "太热了"]

# 假设模型给出"它"和每个词的关联程度（手动设定，仅作演示）
relevance_to_it = {
    "小明": 1, "把": 0, "蛋糕": 7, "放进": 0,
    "冰箱": 2, "因为": 0, "它": 0, "太热了": 0,
}

total = sum(relevance_to_it.values())
print("「它」在读这句话时，注意力分配如下：")
for word in sentence:
    share = relevance_to_it[word] / total
    bar = "█" * int(share * 30)
    print(f"{word:>4} {bar} {share:.0%}")

focus = max(relevance_to_it, key=relevance_to_it.get)
print(f"\n结论：这里的「它」最可能指「{focus}」")
```

输出：

```
「它」在读这句话时，注意力分配如下：
  小明 ███ 10%
   把  0%
  蛋糕 █████████████████████ 70%
  放进  0%
  冰箱 ██████ 20%
  因为  0%
   它  0%
 太热了  0%

结论：这里的「它」最可能指「蛋糕」
```

### 7.4 每个词都在"问一圈"

注意，不只是"它"在问。**句子里每一个词，都会向所有其他词问一圈**：

- "热"会去关注"蛋糕"（谁热？）；
- "放进"会去关注"冰箱"（放进哪？）和"蛋糕"（放什么？）；
- "因为"会去关注前后两个分句（谁是原因？）。

问完之后，每个词的身份卡都被更新了，**不再是孤立的词，而是"在这个句子里的这个词"**。同一个"苹果"，在"吃苹果"里会吸收"吃"的信息变成水果的意思，在"苹果发布会"里会吸收"发布会"的信息变成公司的意思。

### 7.5 多头注意力：好几个侦探一起看

一句话里的关系是多种多样的：谁做了什么（语法关系）、指代关系、情绪关系、时间关系……

所以模型不是只派一个"侦探"去问一圈，而是同时派出好几个、甚至几十个侦探，每个侦探关注的角度不同：

- 1 号侦探专门找"主语和动词"；
- 2 号侦探专门找"代词指谁"；
- 3 号侦探专门看"语气是正面还是负面"；
- ……

这叫 **多头注意力（Multi-Head Attention）**。当然，每个侦探负责什么也不是人规定的，是训练中自己分化出来的。

### 7.6 为什么注意力这么重要？

在注意力机制出现之前，机器读句子像我们用手指一个字一个字地点着读，读到后面就忘了前面。

有了注意力，机器可以**一眼看完整句话（甚至整本书），随时回头找相关的内容**，不管它们隔了多远。这是 LLM 能处理长文章、理解复杂逻辑的根本原因。

## 第八课：Transformer——把注意力叠成流水线

### 8.1 Transformer 是什么？

2017 年，谷歌的研究者发表了一篇论文，标题很霸气：《Attention Is All You Need》（注意力就是你所需要的一切）。论文提出的模型结构叫 **Transformer**。

今天几乎所有的 LLM——GPT 里的 "T"，就是 Transformer——都建立在它之上。

### 8.2 工厂流水线的比喻

把 Transformer 想象成一条加工"身份卡"的流水线：

```
原始文字
   ↓ 切块（Token）
   ↓ 发身份卡（Embedding）+ 标上座位号（位置信息）
┌─────────── 第 1 道工序 ───────────┐
│  开会：每个词问一圈（注意力）      │
│  独自消化：整理刚听到的信息        │
└──────────────────────────────────┘
┌─────────── 第 2 道工序 ───────────┐
│  开会 + 独自消化                  │
└──────────────────────────────────┘
   ……（重复几十到上百道工序）
   ↓
最后一个词的身份卡 → 翻译成"下一个字的候选名单"
```

几个要点：

1. **座位号（位置信息）**："狗咬人"和"人咬狗"用的字一样，意思完全相反。所以每个词除了身份卡，还要标上自己坐在第几个位置。
2. **"开会 + 消化"反复进行**：第一道工序可能只理解了"它指蛋糕"这种浅层关系；到后面的工序，模型能理解更深的东西，比如"这句话是在讽刺"、"这段代码有个 bug"。就像读一本书，读第一遍懂字面意思，读第十遍才懂言外之意。
3. **只看前面，不偷看后面**：做"猜下一个字"的训练时，每个词开会只能问它**前面**的词，不能偷看后面——否则就成了"看答案做题"。

### 8.3 用 Python 描述流水线的骨架

下面这段代码不做真实计算，只用来展示流水线的"形状"：

```python
# 第八课：Transformer 流水线的骨架（示意，不做真实计算）
def attention_meeting(cards):
    """开会：每个词只向它前面的词（包括自己）问一圈，吸收相关信息"""
    new_cards = []
    for i, card in enumerate(cards):
        heard = [c["word"] for c in cards[: i + 1]]  # 只能看到前面的词
        new_cards.append({**card, "heard": card["heard"] + [heard]})
    return new_cards

def digest(cards):
    """消化：每个词独自整理刚听到的信息（这里只是打个标记）"""
    return [{**c, "layers": c["layers"] + 1} for c in cards]

def transformer(words, num_layers=3):
    cards = [{"word": w, "position": i, "heard": [], "layers": 0}
             for i, w in enumerate(words)]          # 身份卡 + 座位号
    for _ in range(num_layers):                     # 一道道工序
        cards = digest(attention_meeting(cards))
    return cards[-1]  # 用最后一个词的身份卡去猜下一个字

last = transformer(["床", "前", "明", "月"])
print(f"最后一个词「{last['word']}」经过了 {last['layers']} 道工序")
print(f"它在第 1 道工序里能看到：{last['heard'][0]}")
```

真实模型里，`attention_meeting` 和 `digest` 里面都是那些"旋钮"在起作用，而工序数通常是几十层。

### 8.4 为什么 Transformer 赢了？

除了注意力本身很强之外，还有一个很实际的原因：**它适合并行计算**。

以前的模型像一个人逐字读书，只能一个字一个字地处理；Transformer 在训练时像一整个班的人同时读书，每人负责一个字，然后一起开会。这让它能充分利用显卡（GPU）同时干活的能力，从而能用海量数据训练出巨大的模型。

**"大"之所以成为可能，Transformer 功不可没。**

## 第九课：训练三部曲——读书、上课、被老师纠正

一个 LLM 从"一张白纸"到"能和你聊天的助手"，通常要经历三个阶段。我们用"培养一个学生"来比喻。

### 9.1 第一阶段：预训练——疯狂读书

**做什么**：让模型阅读几乎整个互联网的文字——百科、新闻、小说、论坛、代码、论文……然后玩上万亿次"猜下一个字"的游戏，不停调整旋钮。

**比喻**：一个孩子被关在一座超级图书馆里，把所有书都读了一遍。他没有老师，只是不停地读、不停地猜下一句。

**学到了什么**：
- 语言的语法和表达方式；
- 大量的世界知识（谁是李白、水的沸点是多少）；
- 一定的推理能力（因为文章里充满了推理过程）；
- 写代码的能力（因为它读了大量代码）。

**这个阶段的问题**：他学会了"接话"，但不会"对话"。你问他"中国的首都是哪里？"，他可能接着写"美国的首都是哪里？日本的首都是哪里？"——因为在他读过的书里，这种问题经常出现在一份"地理练习题"里，下一句自然是另一道题。

这个阶段的模型叫 **基座模型（Base Model）**，它是最花钱、最花时间的部分，可能需要几千块显卡跑几个月。

### 9.2 第二阶段：指令微调——上课学规矩

**做什么**：找人写几万到几十万份高质量的"问答示范"，比如：

```
用户：中国的首都是哪里？
助手：中国的首都是北京。
```

让模型照着这些示范继续训练。

**比喻**：读完图书馆的孩子，被送去一所礼仪学校。老师告诉他："别人问你问题时，你要直接回答，而不是接着出题。"

**学到了什么**：对话的格式、回答问题的方式、听从指令的习惯。

这个阶段叫 **监督微调（SFT, Supervised Fine-Tuning）**。注意，这个阶段主要教的是"**怎么说**"，而不是"**知道什么**"——知识大多在第一阶段就学到了。

### 9.3 第三阶段：人类反馈——被老师打分纠正

**做什么**：让模型对同一个问题写出好几个回答，请人来排序："这个回答最好，那个回答有点啰嗦，另一个回答有害。"然后让模型朝着"人类更喜欢的方向"调整。

**比喻**：学生开始实习，每天写报告交给导师。导师不一定会亲自写范文，但会说："这份比那份好。"久而久之，学生就摸清了导师的偏好。

**学到了什么**：
- 回答更有帮助、更清楚；
- 不说有害的内容；
- 不确定时承认不知道（理想情况下）。

这个阶段常被称为 **RLHF（基于人类反馈的强化学习）**。

### 9.4 用 Python 模拟三个阶段的变化

```python
# 第九课：同一个问题，三个阶段的模型分别会怎么"接话"
question = "中国的首都是哪里？"

def base_model(text):
    # 预训练后：只会接龙，像在续写一份练习题
    return text + "\n美国的首都是哪里？\n日本的首都是哪里？"

def sft_model(text):
    # 指令微调后：知道要回答问题了
    return "中国的首都是北京。北京是一座历史悠久的城市，有故宫、长城、天坛……（继续说了很多）"

def rlhf_model(text):
    # 人类反馈后：回答更符合人的偏好——直接、准确、简洁
    return "中国的首都是北京。"

for stage, model in [("预训练", base_model), ("指令微调", sft_model), ("人类反馈", rlhf_model)]:
    print(f"【{stage}】\n{model(question)}\n")
```

（这里的输出是手写的，用来展示三个阶段的风格差异。）

### 9.5 一张表记住三部曲

| 阶段 | 比喻 | 数据 | 学到什么 |
|------|------|------|------|
| 预训练 | 在图书馆读万卷书 | 海量网络文本 | 语言 + 知识 + 推理 |
| 指令微调 | 去学校学规矩 | 人写的问答示范 | 对话格式、听从指令 |
| 人类反馈 | 导师打分纠正 | 人对回答的排序 | 更有用、更安全 |

## 第十课：生成文字——温度与"掷骰子"

### 10.1 模型给出的不是一个答案，而是一份"候选名单"

前面为了简单，我们说模型"猜出下一个字"。更准确地说，模型每次输出的是一份**候选名单**，上面写着每个字作为下一个字的"把握程度"：

> 输入："今天天气真"
>
> 候选名单：好（60%）、不错（20%）、热（10%）、糟（5%）、……

然后，我们要从名单里**挑一个**。怎么挑？

### 10.2 两种挑法

- **永远挑第一名**：最稳妥，但很死板。每次问同样的问题，回答一字不差；写故事时经常陷入重复。
- **按比例掷骰子**：60% 的概率选"好"，20% 的概率选"不错"……这样回答会有变化，更像人。

这就是为什么你问 ChatGPT 同一个问题两次，答案会不一样——**它每次都在掷骰子**。

### 10.3 温度：控制"冒险精神"的旋钮

**温度（Temperature）** 是一个调节"掷骰子有多随性"的参数：

- **低温度**（比如 0）：几乎总选第一名。像一个谨慎的会计，适合写代码、做数学、提取信息。
- **高温度**（比如 1.5）：冷门的字也有不小的机会被选中。像一个喝了点酒的诗人，适合头脑风暴、写创意文案。但温度太高，就会开始说胡话。

### 10.4 用 Python 感受温度

```python
# 第十课：温度如何影响"掷骰子"
import random

candidates = {"好": 60, "不错": 20, "热": 10, "糟": 6, "紫": 4}

def adjust_by_temperature(scores, temperature):
    """温度低：强者更强；温度高：差距被拉平（这里用乘方做个示意）"""
    if temperature == 0:
        best = max(scores, key=scores.get)
        return {w: (1 if w == best else 0) for w in scores}
    return {w: s ** (1 / temperature) for w, s in scores.items()}

def sample(scores, temperature, times=20):
    adjusted = adjust_by_temperature(scores, temperature)
    words, weights = list(adjusted), list(adjusted.values())
    picks = random.choices(words, weights=weights, k=times)
    return "".join(f"[{p}]" for p in picks)

for t in (0, 0.5, 1.0, 3.0):
    print(f"温度 {t}：今天天气真…… {sample(candidates, t)}")
```

运行结果大致是：

```
温度 0：  全部是 [好]
温度 0.5：绝大多数是 [好]，偶尔有 [不错]
温度 1.0：[好] 为主，[不错]、[热] 时常出现
温度 3.0：五花八门，连 [紫] 都冒出来了——"今天天气真紫"
```

### 10.5 其他挑选策略

除了温度，你可能还会在 API 里看到：

- **Top-K**：只在前 K 名里掷骰子。比如 K=3，那么"糟"和"紫"直接被淘汰。
- **Top-P**：从第一名往下累加，直到把握程度加起来达到 P（比如 90%），只在这些里面掷骰子。

它们的目的都一样：**既要有变化，又不能离谱。**

## 第十一课：LLM 的脾气——幻觉、记忆、知识截止

理解了原理之后，很多 LLM 的"怪脾气"就都说得通了。

### 11.1 幻觉：一本正经地胡说八道

**现象**：你问 LLM 一篇不存在的论文，它可能给你编出标题、作者、发表年份，看起来煞有介事。

**原因**：回想第一课——LLM 的本职工作是"**接出最像样的下一个字**"，而不是"**查证事实**"。论文引用通常长这样："作者名（年份）.《标题》. 期刊名"，它就按这个格式接出了一段"最像论文引用"的文字。它没有"我不知道"的本能，除非在第三阶段被专门训练过。

**比喻**：一个特别想表现的学生，考试遇到不会的题也不愿意空着，于是根据题目风格"编"了一个看起来很合理的答案。

**应对**：
- 重要的事实要自己核对；
- 给模型提供资料，让它"根据资料回答"（这叫 **RAG，检索增强生成**，相当于开卷考试）；
- 在提问时明确告诉它："不确定就说不知道。"

### 11.2 记忆：它其实"记不住"你

**现象**：你在一个对话里告诉它"我叫小王"，新开一个对话，它就不记得了。

**原因**：模型的旋钮在训练完成后就**固定不变**了。你和它聊天，不会改变任何一个旋钮。那它在同一个对话里为什么"记得"你说过的话？因为每次你发消息，**整段聊天记录都会被重新发给它一遍**，它是在"重新读一遍"之后接话的。

我们用 Python 看看聊天程序实际在干什么：

```python
# 第十一课：LLM 的"记忆"其实是每次都把聊天记录重新发一遍
def fake_llm(full_text):
    """假装的 LLM：只能看到传给它的文字"""
    if "我叫小王" in full_text and "我叫什么" in full_text:
        return "你叫小王。"
    if "我叫什么" in full_text:
        return "抱歉，我不知道你叫什么。"
    return "好的，我记住了。"

history = []

def chat(user_message):
    history.append(f"用户：{user_message}")
    full_text = "\n".join(history)      # 关键：把全部历史拼起来发过去
    reply = fake_llm(full_text)
    history.append(f"助手：{reply}")
    return reply

print(chat("我叫小王"))        # 好的，我记住了。
print(chat("我叫什么？"))       # 你叫小王。

history.clear()                # 新开一个对话 = 清空历史
print(chat("我叫什么？"))       # 抱歉，我不知道你叫什么。
```

**这就是 LLM "记忆"的真相：它没有记忆，是聊天程序帮它把记录一次次念给它听。**

### 11.3 上下文窗口：一次能念多长？

既然每次都要把聊天记录重新念一遍，那记录太长怎么办？

每个模型都有一个 **上下文窗口（Context Window）** 的上限，比如 128K 或 200K 个 Token。超过上限的部分，要么被截掉，要么被压缩成摘要。

**比喻**：模型的"工作台"只有这么大，资料太多就放不下了。所以超长的对话里，模型会"忘记"最开头说过的事。

### 11.4 知识截止：它不知道昨天发生了什么

**现象**：问它最近的新闻，它可能不知道，或者给出过时的信息。

**原因**：预训练的"图书馆"是在某个时间点封馆的，之后的书它没读过。这个时间点叫 **知识截止日期（Knowledge Cutoff）**。

**应对**：给它接上搜索工具，让它先查再答——这就引出了最后一课。

### 11.5 其他常见现象，一句话解释

| 现象 | 用原理解释 |
|------|------|
| 数字母、算大数容易错 | 它看到的是 Token 块，不是一个个字母和数位（第四课） |
| 同一个问题，答案每次不同 | 它在掷骰子（第十课） |
| 换个问法，答案质量差很多 | 上下文变了，注意力关注的东西就变了（第七课） |
| 让它"一步一步想"会更准 | 它把中间步骤写出来后，后面的字可以"看着"前面的推理来接（第一、七课） |
| 很会模仿某种文风 | 它在图书馆里读过大量该文风的文字（第九课） |

关于"一步一步想"值得多说一句：LLM 每接一个字，都只"想"了一小下。如果直接让它说出复杂问题的答案，相当于让人不打草稿就心算；让它先把思路写出来，等于给了它一张草稿纸，每一步都能参考前面写下的内容。这个技巧叫 **思维链（Chain of Thought）**，现在的"推理模型"就是把这种"先打草稿"的习惯训练得更彻底。

## 第十二课：怎样和 LLM 打交道——Prompt 与 Agent

### 12.1 Prompt：你给它的"开头"

还记得 LLM 是在"接龙"吗？那么，**你写的问题，就是接龙的开头**。开头写得好，接出来的内容自然就好。这就是 **Prompt（提示词）** 的意义。

对比两种开头：

```
差的开头：写个介绍。

好的开头：你是一名资深旅游编辑。请为第一次去杭州的大学生
写一段 200 字左右的西湖介绍，语气轻松，包含 2 个拍照推荐点。
```

第二个开头里，"资深旅游编辑"让模型联想到它读过的专业旅游文章；"大学生"、"轻松"、"200 字"、"拍照推荐点"都在缩小它的接龙范围。

**写好 Prompt 的几个小技巧**：

1. **说清楚角色**：你希望它以什么身份回答。
2. **说清楚任务**：做什么、给谁看、多长、什么格式。
3. **给出例子**：给一两个你想要的示范，它会照着风格来（这叫 **少样本提示，Few-shot**）。
4. **提供资料**：需要准确事实时，直接把资料贴给它。
5. **让它分步思考**：复杂问题加一句"请一步一步分析"。

### 12.2 在 Python 里怎么调用 LLM？

真实世界里，你通常通过各家厂商提供的 Python SDK 调用模型。不同厂商写法略有区别，但结构大同小异：

```python
# 第十二课：调用真实 LLM 的典型结构（示意，需要安装对应 SDK 和 API Key）
# from some_llm_sdk import Client
#
# client = Client(api_key="你的密钥")
# response = client.chat(
#     model="某个模型名",
#     temperature=0.7,              # 第十课讲的"温度"
#     max_tokens=500,               # 第四课讲的 Token：最多回复多少
#     messages=[                    # 第十一课讲的"聊天记录"
#         {"role": "system", "content": "你是一名资深旅游编辑。"},
#         {"role": "user", "content": "介绍一下西湖，200 字。"},
#     ],
# )
# print(response.text)
```

你会发现，这里的每一个参数，都能在前面的课程里找到对应的原理：
- `temperature` → 掷骰子的随性程度；
- `max_tokens` → 最多接多少个 Token；
- `messages` → 每次都要把聊天记录完整发过去，因为模型自己不记事；
- `system` → 写在最前面的"角色设定"，作为整个接龙的开头。

### 12.3 Agent：给 LLM 装上手和脚

LLM 自己只会"说"，不会"做"。它不能上网、不能读你的文件、不能运行代码。

但聪明的工程师想到了一个办法：**让 LLM 说出"我想用什么工具"，然后由程序替它去执行，再把结果告诉它。**

```
用户：明天北京天气怎么样？
LLM（接龙出）：我需要调用工具 → 查天气("北京", "明天")
程序：（真的去调用天气接口）→ 结果："晴，5~15 度"
程序：把结果拼回聊天记录，再发给 LLM
LLM（接龙出）：明天北京晴，气温 5 到 15 度，早晚较凉，记得加件外套。
```

用 Python 模拟这个"思考 → 用工具 → 再思考"的循环：

```python
# 第十二课：一个最小的 Agent 循环（LLM 用假的代替）
def get_weather(city):
    """假装的天气工具"""
    return {"北京": "晴，5~15 度", "杭州": "小雨，12~18 度"}.get(city, "未知")

tools = {"查天气": get_weather}

def fake_llm(history):
    """假装的 LLM：如果还没有天气结果，就要求用工具；有了就回答"""
    last = history[-1]
    if last.startswith("工具结果："):
        return f"回答：明天天气{last[5:]}，出门注意增减衣物。"
    return "调用工具：查天气|北京"

def agent(question):
    history = [f"用户：{question}"]
    for _ in range(5):                       # 最多来回 5 次，防止死循环
        reply = fake_llm(history)
        print("LLM 说 →", reply)
        if reply.startswith("回答："):
            return reply
        tool_name, arg = reply[len("调用工具："):].split("|")
        result = tools[tool_name](arg)       # 程序替 LLM 去执行工具
        history.append(f"工具结果：{result}")
        print("程序执行 →", result)

agent("明天北京天气怎么样？")
```

输出：

```
LLM 说 → 调用工具：查天气|北京
程序执行 → 晴，5~15 度
LLM 说 → 回答：明天天气晴，5~15 度，出门注意增减衣物。
```

这就是 **Agent（智能体）** 的核心思想。现在的编程助手、自动订票助手、数据分析助手，本质上都是这个循环：**LLM 负责思考和决策，程序负责执行，结果再反馈给 LLM**。工具可以是搜索引擎、计算器、数据库、代码运行器……LLM 的能力边界，就这样被大大扩展了。

## 总结：把十二课串成一条线

让我们用一段话，把整个 LLM 的原理串起来：

> 我们把海量文字**切成 Token**（第四课），给每个 Token 发一张会自己学习的**身份卡**（第五课）。这些身份卡被送进一条叫 **Transformer** 的流水线（第八课），每一道工序里，词与词之间通过**注意力**互相"开会"（第七课），理解彼此的关系。流水线里有几百亿个**旋钮**（第六课），通过上万亿次"**猜下一个字**"的热冷游戏被调好（第二、三、六课），这就是**预训练**；之后再经过**指令微调**和**人类反馈**，学会好好对话（第九课）。使用时，它一个字一个字地**接龙**（第一课），每一步都按**温度**掷骰子挑选（第十课）。因为它本质是"接出最像样的话"，所以会**幻觉**；因为旋钮不再变化，所以**没有记忆**，靠每次重发聊天记录维持对话（第十一课）。最后，用好的 **Prompt** 引导它，再给它装上**工具**，它就成了能干活的 **Agent**（第十二课）。

如果只能记住一句话，那就是：

> **LLM 是一个读过海量文字、极其擅长"接下一个字"的机器。它所有的能力和所有的毛病，都从这一点出发。**
